# Constraints and Assumptions

## Hard constraints

1. Branch is `staging`.
2. Keep one Appwrite staging project.
3. Keep one staging database.
4. Keep current user records.
5. Keep current Admin role validation.
6. `api-staging.marketiv.id` remains the user-app API hostname.
7. Admin should use `api-admin-staging.marketiv.id`.
8. No production changes.
9. No unrelated refactor.
10. No secret committed to Git.

## Assumptions that MUST be verified

### A1
`staging.marketiv.id` currently uses:

```text
NEXT_PUBLIC_APPWRITE_ENDPOINT=https://api-staging.marketiv.id/v1
```

If not, record the actual value before making changes.

### A2
`admin-staging.marketiv.id` currently points to the same Appwrite endpoint/project as the user app.

### A3
Appwrite Cloud permits adding `api-admin-staging.marketiv.id` as another API custom domain for the same staging project.

Do not assume; confirm in Console.

### A4
Appwrite-created browser session cookies on the two custom API hosts remain host-isolated.

Verify this in browser DevTools after deployment.

### A5
Google OAuth on the user app is already configured against the callback URL generated by Appwrite for the user-app API hostname.

If main Appwrite API hostname does not change, no Google redirect modification is expected.

## Stop conditions

Stop implementation and report a blocker if:

- the second API custom domain cannot be created for the same project;
- Appwrite forces both API domains to share a `.marketiv.id` session cookie that still collides;
- deployed env values unexpectedly point the apps at different Appwrite projects;
- fixing the issue would require production changes;
- fixing requires a broad auth architecture migration not covered by this spec.

Do not silently choose a new project or SSR migration.
