# Implementation Notes

## 1. Appwrite custom domains

In the staging Appwrite project:

- retain `api-staging.marketiv.id`;
- create `api-admin-staging.marketiv.id` as an Appwrite API custom domain;
- use the exact CNAME/CAA data generated by Appwrite Console;
- verify domain and TLS certificate before switching Admin env.

Do not guess the CNAME target.

## 2. Web platform / allowed domains

Verify Appwrite's current project configuration accepts both frontend origins:

- `staging.marketiv.id`
- `admin-staging.marketiv.id`

If Appwrite exposes an Allowed Domains setting for the project, ensure the required origins are present according to current Console behavior.

## 3. Admin deployment environment

Change only Admin staging Site:

```dotenv
NEXT_PUBLIC_APPWRITE_ENDPOINT=https://api-admin-staging.marketiv.id/v1
```

Keep project/database IDs equal to main staging.

Redeploy Admin after environment change.

## 4. Main deployment environment

Expected:

```dotenv
NEXT_PUBLIC_APPWRITE_ENDPOINT=https://api-staging.marketiv.id/v1
```

If already correct, do not change it and do not redeploy solely for this reason unless operationally required.

## 5. Google OAuth

### Do not change Google OAuth merely because Admin gets a new API hostname.

Admin currently has no Google OAuth requirement.

Main Google OAuth should continue through:

```text
api-staging.marketiv.id
```

if that is already its Appwrite API hostname.

### Verification only

In Appwrite Console:
- Auth
- Settings
- Google OAuth provider
- copy the redirect URL Appwrite displays

In Google Cloud OAuth client:
- Authorized redirect URI must match the current Appwrite-provided callback URL.

If `api-staging.marketiv.id` remains unchanged and the callback already matches, make **zero changes**.

Never guess the provider callback path.

## 6. Browser verification

After deployment inspect DevTools:

- Application/Storage → Cookies
- Local Storage if Appwrite falls back there
- Network requests to `/account/*`

Confirm:
- user app requests hit `api-staging.marketiv.id`;
- admin requests hit `api-admin-staging.marketiv.id`;
- session storage/cookie for one does not get replaced by the other;
- cookie scope is not unexpectedly `.marketiv.id`.

## 7. Tests

Do not weaken existing admin auth tests.

Add only regression tests that are meaningful at code level.

Cross-host cookie isolation itself requires deployed browser/E2E/manual verification; a mocked unit test cannot prove browser cookie scoping.
